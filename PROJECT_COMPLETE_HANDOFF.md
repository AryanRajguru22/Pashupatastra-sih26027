## 2. Problem Statement

Real-world problem (from `docs/demo-script.md`, `README.md`): Indian Railways must
run engineering maintenance — track renewal, ballast tamping, overhead-electrification
work, signalling checks — without stopping trains. Every maintenance job competes for
scarce **possession windows** (time slots when a track is taken out of traffic).
Today this scheduling is largely manual; when a disruption occurs (asset failure,
track closure, emergency repair) the plan must be manually reworked under pressure.

**Why it matters (project's own framing):** manual re-planning under time pressure is
slow and error-prone; an automated system that (a) scores work by priority/risk and
(b) builds a mathematically conflict-free schedule, then (c) automatically
re-computes a new feasible plan on disruption, reduces this operational burden.

**Inputs (using the project's own contract terms), per `contracts/schemas.py` /
`docs/contracts.md`:**
- `BlockCandidate` — a maintenance job: `block_id`, `asset_id`, `track_id`,
  `work_type`, `duration_minutes`, `earliest_start_minute`, `latest_end_minute`,
  `priority_score`, `risk_score`, `dependencies`, `mutual_exclusion_group`,
  `is_committed`, `status`, `metadata`.
- `PossessionWindow` — an available maintenance time slot on a track (`window_id`,
  `track_id`, `start_minute`, `end_minute`, `window_type`).
- `OptimizationRequest` — `corridor_id`, `horizon_minutes`, `tracks`, `candidates`,
  `possession_windows`, `existing_committed_blocks`, `min_headway_minutes`,
  `train_timetable`.
- `DisruptionEvent` — a real-time change to apply to a plan (`disruption_type`,
  `track_id`, `affected_asset_id`, `new_candidate`, time window).

**Outputs:**
- `OptimizationResult` — `status` (`OPTIMAL`/`FEASIBLE`/`INFEASIBLE`/`NO_SOLUTION`),
  `scheduled_blocks` (as `ScheduledBlock` with concrete `start_minute`/`end_minute`/
  `track_id`), `unscheduled_blocks`, `total_priority_scheduled`,
  `total_risk_mitigated`, `solve_time_seconds`, `infeasibility_reasons`,
  `rejection_reasons` (per-block textual reason it was not scheduled).
- `RecoveryResponse` — the disruption applied, the mutated `updated_request`, and a
  fresh `recovery_result` (`OptimizationResult`).

**Decisions supported:** which candidate maintenance jobs get a track+time slot
today (PLAN), what happens to the plan when a named disruption occurs (DISRUPT),
and what the system automatically re-computes as the new feasible plan (RECOVER) —
this is literally the demo narrative baked into the UI stage names
(`OperationalStage = "PLAN" | "DISRUPT" | "RECOVER"`, `frontend/src/lib/stage.ts`).

## 3. Complete System Overview

### 3.1 Normal optimization flow (PLAN)

1. **Input**: an `OptimizationRequest` JSON body (either a canonical fixture such as
   `backend/app/data/fixtures/corridor_a_blocks.json`, or a request built by the
   synthetic generator `CorridorDataGenerator`).
2. **Validation**: FastAPI/Pydantic-adjacent validation via the plain-dataclass
   `OptimizationRequest.model_validate` call used in `backend/app/api/deps.py`
   (dataclasses used directly as FastAPI request/response types — FastAPI 0.141.1
   supports standard-library dataclasses natively). Malformed bodies return HTTP 422
   (verified by `test_optimize_invalid_request_returns_422` and
   `test_recover_malformed_request_returns_422`).
3. **Feature enrichment/scoring** (only happens ahead of time, when data is
   *generated*, not inside `/optimize` itself): `CorridorDataGenerator` in
   `backend/app/data/generator.py` calls `ScoringFeatureAdapter.score_domain_block()`
   (`backend/app/data/feature_adapter.py`) which builds the 7 canonical scoring
   features and calls `score_block()` (`backend/app/ml/scorer.py`) to fill in
   `priority_score`/`risk_score` on each generated `BlockCandidate`. **Important:**
   the live `/optimize` endpoint itself does **not** call the scorer — it assumes
   `priority_score`/`risk_score` already exist on the incoming candidates (they are
   pre-computed into the fixtures/generated data). This is a real architectural
   detail, not an oversight description — see Section 6/7.
4. **Optimization**: `POST /optimize` (`backend/app/api/routers/optimize.py`) calls
   `backend.app.optimizer.solver.solve(request)` directly — a thin wrapper with no
   logic of its own. `solve()` builds a Google OR-Tools CP-SAT model, enforces hard
   constraints, maximizes an objective, and returns an `OptimizationResult`.
5. **API response**: the `OptimizationResult` dataclass, serialized to JSON by
   FastAPI's `response_model=OptimizationResult`.
6. **Frontend visualization**: `frontend/src/lib/data.ts` `fetchOptimizationData()`
   POSTs a canonical fixture request to `${API_BASE_URL}/optimize`; on success it
   enriches the result with request-candidate metadata (`enrichData()`) and renders
   it via `DashboardClient` → `PlanView` (a schedule visualization plus block
   selection/detail).

### 3.2 Disruption/recovery flow (DISRUPT → RECOVER)

1. User selects one of 4 disruption types in the UI (`DisruptRecoverView.tsx`) and
   supplies the relevant parameters (track, asset, time window, or a new emergency
   candidate).
2. Frontend calls `triggerRecovery()` (`frontend/src/lib/data.ts`), which POSTs
   `{ request, disruption }` (matching `contracts.RecoveryRequest`) to
   `${API_BASE_URL}/recover`.
3. Backend `POST /recover` (`backend/app/api/routers/recover.py`) calls
   `simulate_disruption(request, disruption)`
   (`backend/app/simulation/simulator.py`), which:
   a. calls `apply_disruption(request, event)`
      (`backend/app/simulation/disruptions.py`) to produce a mutated
      `OptimizationRequest` (candidates/committed-blocks/possession-windows
      changed depending on disruption type — never mutates the original request
      object, always works on a deep copy via `OptimizationRequest.from_dict(request.to_dict())`);
   b. calls `solve(updated_request)` — the exact same CP-SAT solver used by
      `/optimize`, no separate recovery-specific solving logic.
4. Backend returns `RecoveryResponse` (`disruption`, `updated_request`,
   `recovery_result`).
5. Frontend computes a BEFORE→AFTER comparison **client-side**
   (`frontend/src/lib/recoveryComparison.ts`, `compareSchedules()`), classifying
   every changed block as `PRESERVED` / `MOVED` / `NEWLY_SCHEDULED` / `DROPPED` by
   diffing the two `OptimizationResult.scheduled_blocks` lists — this comparison
   logic does not exist on the backend; it is purely a frontend computation over two
   real backend results.
6. `DashboardClient` swaps the visible plan to the recovered one and stage becomes
   `RECOVER`; a "Return to Original Plan" action resets to the pre-disruption
   `baselineData` state held in React state (no backend call involved in reverting).

## 6. Optimization / Scheduling Engine

**File:** `backend/app/optimizer/solver.py`, function `solve(request: OptimizationRequest) -> OptimizationResult`.

**Library:** Google OR-Tools CP-SAT (`from ortools.sat.python import cp_model`),
version installed in this environment: **ortools 9.15.6755** (requirement pin in
`requirements.txt`: `ortools>=9.9`).

**What's optimized:** presence (schedule/don't-schedule) and start/end time (in
integer minutes, relative to a `horizon_minutes` planning window) for every
`BlockCandidate` in the request.

**Decision variables per block:**
- `presence_{block_id}` — `BoolVar`, whether the block is scheduled at all.
- `start_{block_id}`, `end_{block_id}` — `IntVar`s bounded by the block's own
  `earliest_start_minute`/`latest_end_minute` window (clamped to the horizon).
- If `latest_start < earliest` (duration cannot fit in its own window), the block is
  forced `presence == 0` and pinned to a degenerate 0-length interval — this keeps
  CP-SAT domains valid rather than producing an infeasible model outright.

**Hard constraints enforced (verified in code, each cross-checked by a
`backend/tests/test_solver.py` or `test_optimizer_reoptimization.py` test):**
1. **Block time window** — `end == start + duration`, both bounded to
   `[earliest_start_minute, latest_end_minute]`.
2. **Possession-window containment** — a block may only be scheduled if its
   `[start, end]` lies completely inside at least one `PossessionWindow` on the same
   track (`start >= window_start`, `end <= window_end`, enforced via a per-window
   boolean `OnlyEnforceIf` selector, with `sum(eligible_windows) == presence[block]`).
   If a block's track has possession windows defined but none can contain it, the
   block is forced `presence == 0`. If a track has *no* possession windows at all in
   the request, this constraint is skipped entirely for that track (no restriction).
3. **Track no-overlap + minimum headway** — per track, all scheduled blocks' buffered
   intervals (`duration + min_headway_minutes`) must not overlap
   (`model.AddNoOverlap` on `NewOptionalIntervalVar`s gated by `presence`).
4. **Dependency ordering** — for each `dependencies` entry (only entries that
   resolve to a known candidate ID are enforced): the dependent cannot be present
   unless its dependency is present (`presence[dependent] <= presence[dependency]`),
   and if present, `start[dependent] >= end[dependency]`.
5. **Mutual-exclusion groups** — all blocks sharing the same
   `mutual_exclusion_group` string (e.g. `CSM_TAMPER_01`, `TOWER_WAGON_01`,
   `S_T_GANG_01` — shared machine/crew) get a `NoOverlap` constraint across their
   intervals, corridor-wide (not per-track — two blocks in the same mutex group on
   *different* tracks still cannot overlap in time).
6. **Committed-block pinning** — for any candidate whose `block_id` is also present
   in `request.existing_committed_blocks`, `presence` is forced to 1 and
   `start`/`end` pinned to the committed block's exact placement (preferring
   `metadata["committed_start_minute"]`/`metadata["committed_end_minute"]` if
   present, else the committed candidate's own `earliest_start_minute` +
   `duration_minutes`). This is what keeps already-locked-in work stable across a
   re-optimization after a disruption.

**Objective function:** `Maximize(sum(round(1000 * (block.risk_score + block.priority_score)) * presence[block]))`
— i.e., a scheduled block contributes its `risk_score + priority_score` (equally
weighted, summed, no separate weighting knobs) to the objective; the code comment
explicitly notes: "The new shared contract does not expose separate objective-weight
configuration, so risk and priority are combined directly." (This is a real,
intentional simplification relative to the unused Pydantic draft contract's
`ObjectiveWeights` model in `contracts/common.py`, which is never actually consulted
by the solver.)

**Solver configuration:** `solver.parameters.max_time_in_seconds = 10.0`. No
`random_seed` or `num_search_workers` is set (confirmed by reading the full file —
these parameters do not appear anywhere in `solver.py`). This matches the prior-session
lead about a potential non-determinism source; see Section 16 for the actual
determinism test result observed in this review.

**Solver status mapping:**
| CP-SAT native status | Mapped `SolverStatus` |
|---|---|
| `OPTIMAL` | `OPTIMAL` |
| `FEASIBLE` | `FEASIBLE` |
| `INFEASIBLE` | `INFEASIBLE` |
| `UNKNOWN` (or anything unmapped) | `NO_SOLUTION` |

If status is not `OPTIMAL`/`FEASIBLE`, the result returns **all** candidates as
unscheduled with a blanket `"solver found no feasible solution"` reason for every
block, `infeasibility_reasons = ["solver found no feasible solution"]`, and zero
totals — no partial/attempted-schedule fallback.

**Rejection-reason ("why wasn't this block scheduled") logic, in priority order,
computed post-solve, not by CP-SAT itself:**
1. `"duration does not fit within earliest_start_minute/latest_end_minute window"` —
   window-infeasible block.
2. `"dependency not scheduled: <dep_id>"` — an unscheduled dependency exists.
3. `"mutual exclusion group conflict with scheduled block: <other_id>"` — another
   block in the same mutex group is scheduled.
4. `"lower objective value than scheduled competing block: <other_id>"` — a
   same-track scheduled block exists with a higher combined risk+priority score.
5. `"excluded by optimizer: capacity/priority trade-off"` — generic fallback when no
   more specific reason is found (e.g., competing block has a lower/equal score but
   still won the solve, or no same-track competitor was found — this is a heuristic
   *post-hoc explanation*, not the solver's actual internal reasoning; CP-SAT does
   not expose a native "why not" trace, so this is reconstructed from the final
   assignment).

**Status values used throughout:** `PLANNED`, `SCHEDULED`, `COMMITTED`, `AFFECTED`,
`UNSCHEDULED`, `CANCELLED` (`BlockStatus` enum, `contracts/schemas.py`). Scheduled
blocks get `COMMITTED` if `is_committed` (either originally or pinned during this
solve) else `SCHEDULED`.

**Solver outputs:** `OptimizationResult` with `scheduled_blocks` (as `ScheduledBlock`
— concrete `track_id`/`start_minute`/`end_minute`/`work_type`/scores/status),
`unscheduled_blocks` (the original `BlockCandidate` objects, unscheduled),
`total_priority_scheduled`/`total_risk_mitigated` (sums over scheduled blocks, each
rounded to 3 decimals), `solve_time_seconds` (`solver.WallTime()`, real CP-SAT wall
time), `rejection_reasons` (dict keyed by block ID).

**Verified invariant tests** (`backend/tests/test_solver.py`): no two scheduled
blocks overlap on the same track (respecting headway); dependencies are ordered and
both scheduled; mutually-exclusive blocks never overlap; no block is scheduled
outside its own window; scheduled+unscheduled exactly partition all candidates;
totals match a recomputation from the request; solved statuses are only
`SCHEDULED`/`COMMITTED`; **solving does not mutate the input request**
(`test_solver_does_not_modify_request`).

**Re-optimization-specific tests** (`backend/tests/test_optimizer_reoptimization.py`):
committed blocks remain at their existing slot across a re-solve; non-committed
blocks move around a committed block when needed; committed blocks still respect
track no-overlap with each other; a non-committed block moves when its old slot
becomes unavailable; the objective genuinely prefers a higher risk+priority block
when only one of two conflicting blocks can fit; two conflicting committed blocks
correctly return `INFEASIBLE`; each of the 4 rejection-reason categories is
exercised with a dedicated test; result totals match scheduled blocks; scheduled
blocks carry "useful explanation fields" (i.e. non-empty status/score data);
solver determinism (see Section 16).

## 7. ML / Scoring System

**This is a deterministic, hand-weighted, explainable heuristic scorer — not a
trained machine-learning model.** The module docstring in
`backend/app/ml/scorer.py` states this outright: "This is the Phase 1 explainable
baseline. The scorer does NOT create a schedule. It only produces: priority_score,
risk_score, explanations." There is no model training code, no serialized model
weights file, no inference framework (scikit-learn/PyTorch/TensorFlow do not appear
anywhere in `requirements.txt` or the codebase). Calling it "AI/ML" (as the README
and `docs/architecture.md` do) is the project's own marketing/demo terminology for
what is, functionally, a documented linear weighted-sum scoring formula over
normalized features — this document uses "deterministic scoring" as the precise
technical description and preserves "AI/ML" only where quoting the project's own docs.

**Entry point:** `score_block(block: Mapping[str, Any]) -> dict[str, Any]`
(`backend/app/ml/scorer.py`).

**Exact 7 input features** (`backend/app/ml/features.py`, `extract_features()`),
each normalized to `[0.0, 1.0]`:
| Feature | Normalization |
|---|---|
| `asset_criticality` | qualitative LOW/MEDIUM/HIGH/CRITICAL → 0.25/0.50/0.75/1.00, or numeric passthrough clamped to [0,1] |
| `defect_severity` | same LOW/MEDIUM/HIGH/CRITICAL mapping |
| `days_overdue` | `clamp(days / 30)` — 30+ days overdue saturates at 1.0 |
| `failure_probability` | accepts either a 0–1 fraction or a 0–100 percentage, normalized to 0–1 |
| `train_impact` | same LOW/MEDIUM/HIGH/CRITICAL mapping |
| `maintenance_duration` | `clamp(duration_minutes / 240)` — 240+ minutes saturates at 1.0 |
| `historical_failure_rate` | same probability normalization as `failure_probability` |

**Two separate weighted sums** (`RISK_WEIGHTS` and `PRIORITY_WEIGHTS` in
`scorer.py`, each set of 7 weights sums to 1.0):

Risk weights: asset_criticality 0.20, defect_severity 0.25, days_overdue 0.10,
failure_probability 0.20, train_impact 0.10, maintenance_duration 0.05,
historical_failure_rate 0.10.

Priority weights: asset_criticality 0.20, defect_severity 0.20, days_overdue 0.20,
failure_probability 0.10, train_impact 0.15, maintenance_duration 0.05,
historical_failure_rate 0.10.

`weighted_score()` computes `sum(feature * weight)`, clamped to `[0,1]`.
`score_level()` buckets a score into `LOW` (<0.50) / `MEDIUM` (0.50–0.74) / `HIGH`
(≥0.75). `build_explanation()` returns up to 4 human-readable labels
(`FEATURE_LABELS` dict, e.g. "High asset criticality", "Severe defect") for
features scoring ≥0.75, sorted by contribution, falling back to the single highest
feature if none clear that bar — this is the "explainability" data surfaced in the
frontend's Decision Audit / Explainability panel.

**What the scores represent:** `priority_score` = how urgently the work should be
done (weighted toward overdue-ness and train impact); `risk_score` = likelihood/
severity of asset failure if deferred (weighted toward defect severity and failure
probability). Both are `[0,1]` floats attached to each `BlockCandidate`.

**Effect on optimization:** `priority_score + risk_score` is the sole per-block
contribution to the CP-SAT objective function (Section 6) — scores are an objective
input only, never a hard constraint, consistent with the project's stated design
principle.

**Domain-to-scorer bridge:** `ScoringFeatureAdapter`
(`backend/app/data/feature_adapter.py`) converts real domain objects (`Asset`,
`TrackSegment`) into the above 7 features (with its own sub-formulas for
`asset_criticality`, `failure_probability`, `train_impact`, etc., documented in
Section 9), then calls `score_block()`. It exposes `build_scorer_input()`,
`score_domain_block()`, and `score_block_candidate()` (the latter resolves a
`BlockCandidate` against a `Corridor`'s asset/track data and writes the computed
`priority_score`/`risk_score`/`metadata` back onto it). `days_overdue` and
`maintenance_duration` are explicitly passed to `score_block()` in **raw units**
(not pre-normalized) — the adapter's docstring/comment states the scorer owns all
normalization, to avoid double-normalization bugs.

**Fixture/scoring alignment work (verified, real):** commit `bdd05e0` ("fix: align
fixtures with canonical scoring pipeline") and the regression test
`backend/tests/test_fixture_scores_match_canonical.py` exist specifically because
`corridor_a_blocks.json`, `corridor_b_dense.json`, and `corridor_c_disrupted.json`
were originally generated **before** `generator.py` was wired to call the canonical
`score_block()`, and had drifted. The test now asserts, for every candidate
(including committed blocks) in those 3 fixtures, that the stored
`priority_score`/`risk_score` equals what `score_block()` recomputes from that same
block's `metadata.scoring_features` (to 4 decimal places). `golden_scenario.json` is
explicitly excluded from this check — its docstring/comment states it is a
hand-authored narrative fixture, not generator output.

**Explainability data surfaced downstream:** each generated `BlockCandidate`'s
`metadata` carries `scoring_features` (the 7 raw inputs) and `scoring_explanation`
(the human-readable reason list) — this is what the frontend's block-detail /
Decision Audit panel reads to show "why this score" per block.

## 8. Disruption & Recovery System

**Enum (`contracts/schemas.py`, `DisruptionType`) — the only 4 disruption types the
live backend actually supports:**
| Type | What it does (verified in `backend/app/simulation/disruptions.py`) |
|---|---|
| `ASSET_BREAKDOWN` | Removes every candidate **and** every committed block whose `asset_id` equals `event.affected_asset_id`. No-op if `affected_asset_id` is not set. |
| `TRACK_UNAVAILABLE` | Removes every candidate and committed block whose `track_id` equals `event.track_id`. No-op if `track_id` is not set. |
| `EMERGENCY_WORK` | Appends `event.new_candidate` (deep-copied, `status` forced to `PLANNED`) to the candidate list, unless a candidate with that `block_id` already exists. No-op if `new_candidate` is `None`. |
| `POSSESSION_CURTAILMENT` | Removes every `PossessionWindow` on the matching track (or all tracks if `track_id` is unset) that time-overlaps `[event.start_minute, event.end_minute]`. |

Any other `disruption_type` string raises `ValueError("Unsupported disruption type: ...")`,
which the `/recover` router turns into HTTP 400. Note: the fixture file
`backend/app/data/fixtures/disruption_scenarios.json` documents 5 narrative
scenarios, including `ASSET_CONDITION_DETERIORATION` and `INFEASIBLE_SCENARIO` —
these are **not** implemented `DisruptionType` values and would be rejected by the
live `/recover` endpoint (confirmed: `test_recover_unsupported_disruption_type_returns_400`
uses exactly `"ASSET_CONDITION_DETERIORATION"` as its 400-triggering example). This
fixture file is a design/testbed document that outpaces what's actually wired up —
flagged as a real known discrepancy, not fabricated.

**Recovery workflow** (`backend/app/simulation/simulator.py`,
`simulate_disruption()`):
1. `apply_disruption(request, event)` → mutated `OptimizationRequest` (always
   operates on a `copy.deepcopy`-equivalent independent copy via
   `OptimizationRequest.from_dict(request.to_dict())`; the original request is never
   mutated — verified by `test_disruption_does_not_mutate_original_request`).
2. `solve(updated_request)` — the identical CP-SAT solver function used by
   `/optimize`. Committed blocks in the mutated request are still pinned exactly as
   in a normal solve (Section 6, constraint 6) — this is how "committed work stays
   locked across a disruption" is actually implemented; there is no
   disruption-specific pinning logic.
3. Returns `RecoverySimulation(event, updated_request, recovery_result)`.

**Before/after/recovered plan relationship:** "before" = the plan from the last
`/optimize` call (frontend's `baselineData`); "updated_request" = what `/recover`
returns as the mutated input (with the disruption's structural changes already
applied — e.g. blocks physically removed from the candidate list for
`ASSET_BREAKDOWN`/`TRACK_UNAVAILABLE`, or a new candidate appended for
`EMERGENCY_WORK`); "recovery_result" = the fresh `OptimizationResult` from re-solving
that updated request. The backend does **not** compute a diff/comparison between
before and after — that is entirely a frontend computation.

**Comparison logic (frontend-only, `frontend/src/lib/recoveryComparison.ts`,
`compareSchedules(before: DashboardData, after: DashboardData)`):**
- **PRESERVED** — block ID present in both `scheduled_blocks` lists with identical
  `track_id`/`start_minute`/`end_minute`.
- **MOVED** — present in both, but track or time differs.
- **DROPPED** — was scheduled before, not scheduled after. Reason: if the block ID
  no longer exists as a candidate at all in the "after" request, reason is
  `"Removed by disruption"`; if it's still a candidate but the solver didn't fit it,
  the real per-block `rejection_reasons` string from the recovery result is reused
  (never invented text).
- **NEWLY_SCHEDULED** — scheduled after but not before (e.g. an emergency-work
  candidate that fit, or a slot freed up by a removed competitor).

Aggregate comparison fields returned: `before_status`/`after_status`,
`before_scheduled_count`/`after_scheduled_count`,
`before_unscheduled_count`/`after_unscheduled_count`, full `changes[]` list, and
`preservedCount`/`movedCount`/`newlyScheduledCount`/`droppedCount`.

**How the frontend receives results:** `DashboardClient.handleTriggerDisruption()`
calls `triggerRecovery()` (a real `fetch` POST to `/recover`, no mock/fixture
fallback — `frontend/src/lib/data.ts` explicitly documents "Recovery has no fixture
fallback: it is an explicitly live 'what-if' action, so an unreachable/erroring
backend must be reported to the caller rather than silently substituted"), then
calls `enrichData()` on the result and `compareSchedules()` against the retained
`baselineData`, then updates React state to show the recovered plan. "Return to
Original Plan" (`handleReturnToOriginal`) simply restores `baselineData` from React
state — no backend call.

**Backend test coverage for this system**
(`backend/tests/test_simulation.py`, `backend/tests/test_recover_api.py`): each of
the 4 `apply_*` functions individually; that a disruption never mutates the original
request; that `simulate_disruption()` returns a full recovery result; that an
unsupported type is rejected; and, over real HTTP via `TestClient`, that each of the
4 disruption types produces a 200 response with the expected candidate-list/window
changes, that an unsupported type returns 400, that malformed/missing bodies return
422, and that adding the `/recover` router did not change `/optimize` behavior.

## 9. Data Models & Contracts

### 9.1 The live, actually-used contract surface: `contracts/schemas.py`

Plain Python `@dataclass` types (not Pydantic `BaseModel`s), each with hand-written
`to_dict()`/`from_dict()`. Exported via `contracts/__init__.py`. **This is the only
contract module imported anywhere in the live backend, simulation, or API code** —
confirmed by grepping every `from contracts...` import in the repo.

Core entities:
- **Enums:** `WorkType` (6 values: TRACK_RENEWAL, BALLAST_TAMPING,
  OHE_MAINTENANCE, SIGNALLING_INTERLOCKING, ROUTINE_INSPECTION,
  EMERGENCY_REPAIR), `DisruptionType` (4 values, Section 8), `SolverStatus` (4
  values, Section 6), `BlockStatus` (6 values, Section 6).
- **`PossessionWindow`** — a maintenance time slot on a track.
- **`BlockCandidate`** — a maintenance job request (fields listed in Section 2).
- **`ScheduledBlock`** — a `BlockCandidate` that has been given a concrete
  `track_id`/`start_minute`/`end_minute`.
- **`OptimizationRequest`** — the full solve input (fields in Section 2), including
  an unused-by-the-solver `train_timetable: List[Dict]` field (present in the

  `feature_adapter.py` — a placeholder for a not-yet-implemented capability).
- **`OptimizationResult`** — the full solve output (fields in Section 2).
- **`DisruptionEvent`** — `disruption_id`, `disruption_type`, `corridor_id`,
  optional `track_id`/`affected_asset_id`/`new_candidate` (a `BlockCandidate`),
  `start_minute`/`end_minute`, `description`.
- **`RecoveryRequest`** — `{ request: OptimizationRequest, disruption: DisruptionEvent }`,
  the `/recover` POST body.
- **`RecoveryResponse`** — `{ disruption, updated_request, recovery_result }`, the
  `/recover` response body.

are imported only by each other and by `backend/app/simulation/disruptions.py`'s...

## 12. End-to-End User Flow

### A. Normal optimization (PLAN)

1. Operator opens `http://localhost:3000`.
2. Server-side, `fetchOptimizationData()` POSTs the `corridor_a_blocks.json`
   fixture request to the backend's `/optimize`.
3. If the backend is reachable, the live CP-SAT solve runs (typically single-digit
   milliseconds, per `docs/demo-script.md` and this review's own test-run timings)
   and the header badge shows "LIVE BACKEND: CONNECTED" (`AppHeader.tsx`); if not,
   the badge shows "FIXTURE MODE: OFFLINE" and a checked-in fixture result is shown
   instead.
4. `PlanView` renders every scheduled block on its track/time position, with
   KPI-style aggregate numbers (scheduled count, corridor capacity %, risk
   neutralized %) computed from the real result, not hardcoded.
5. Clicking a block selects it (`selectedBlockId` state) — the UI can show that
   block's `priority_score`/`risk_score`/`metadata.scoring_explanation` (its
   scoring inputs and the reasons that scoring produced), and for an unscheduled
   block, its real `rejection_reasons` text from the solver.
6. "Re-Run Optimization" (`onReoptimize`) re-calls `/optimize` fresh.

### B. Disruption and recovery (DISRUPT → RECOVER)

1. Operator navigates to the Disruption Simulation view (`onNavDisrupt` /
   `onGoToDisrupt`), stage becomes `DISRUPT`.
2. Operator picks one of the 4 real disruption types and fills in the relevant
   parameters (track ID, asset ID, time window, or emergency-work details) in
   `DisruptRecoverView`.
3. Operator triggers the disruption; the UI calls `triggerRecovery()` → real
   `POST /recover` HTTP call.
4. Backend applies the disruption (structurally mutating the request per Section 8)
   and re-solves with CP-SAT (identical solver to `/optimize`); returns
   `RecoveryResponse`.
5. If the call fails (network error or non-2xx), a real error message is shown
   (`recoveryError` state) — not a fabricated success.
6. On success, stage becomes `RECOVER`; the UI shows the before/after comparison
   (`compareSchedules()` output): scheduled/unscheduled counts before vs. after,
   and every changed block classified PRESERVED/MOVED/NEWLY_SCHEDULED/DROPPED with
   real reasons.
7. "Return to Original Plan" (`onReturnToOriginal`) restores the pre-disruption
   `baselineData` from React state (no backend call) — the underlying request data
   was never destroyed since the disruption is only applied to a copy.

test 5 times in isolation in this session — **all 5 runs passed** (`1 passed` each
time, ~0.7–1.2s each). No flakiness was observed in this review. The underlying
theoretical risk described in the prior-session lead is real and independently
confirmed by reading `solver.py`: `cp_model.CpSolver()` is constructed with only
`max_time_in_seconds` set — no `random_seed` or `num_search_workers` parameter
appears anywhere in the file, so CP-SAT's default parallel-portfolio search could in
principle produce tie-breaking differences between runs on a machine/build where
timing varies enough to change which search worker reports first. This review's 5
consecutive passes do not prove the test can never flake elsewhere (e.g. under
different CPU load or a different OR-Tools build); if it starts flaking, pinning
`solver.parameters.random_seed` and `num_search_workers = 1` in `solver.py` would be
the direct fix, but this document does not apply that fix since implementation
changes were out of scope for this review.

## 20. Known Limitations & Honest Boundaries

These are limitations actually observed in the code/docs during this review, not a
generic checklist:

- **No live telemetry, SCADA, or signalling integration.** Confirmed absent from
  every backend module read; explicitly called out as deliberately excluded in the
  `c81c406` commit message and `docs/demo-script.md`'s "what this script
  deliberately does NOT claim" section.
- **No live train-timetable or train-tracking integration.** The
  `OptimizationRequest.train_timetable` field exists on the contract but is never
  populated by the generator or read by the solver/simulation code — it is a
  placeholder, not a working feature. `docs/demo-script.md` explicitly disclaims
  "No claim of live train-timetable integration beyond the `train_impact` scoring
  feature already used in prioritization."
- **No machine/crew capacity limits beyond binary mutual exclusion.**
  `docs/demo-script.md` states this explicitly: only "no two jobs on the same
  machine/crew group at the same time" is implemented — there is no "max N jobs per
  machine per day" style capacity constraint anywhere in `solver.py`. The
  machine-group mutual-exclusion logic itself is a real, tested hard constraint
  (Section 6, constraint 5) — the limitation is specifically the absence of any
  capacity/quota constraint on top of it.
- **No multi-corridor scheduling in one solve.** Every `OptimizationRequest` /
  `solve()` call operates on a single `corridor_id`'s tracks; the generator produces
  separate scenario objects per corridor (A/B/C), and nothing in `solver.py` or the
  API layer accepts or reasons about multiple corridors simultaneously.
- **No temporal replay / historical audit trail beyond the single before/after
  comparison.** The frontend's recovery comparison is a one-shot before-vs-after
  diff computed client-side; there is no persisted history of multiple disruptions
  or a scrubber through time (the `c81c406` commit explicitly names the "temporal
  replay scrubber" as something removed because it had no real backing).
- **Solver has a real 10-second internal time limit** (`_SOLVE_TIME_LIMIT_SECONDS = 10.0`
  in `solver.py`); on a large enough problem this could return `FEASIBLE` (not
  necessarily provably `OPTIMAL`) or, in the worst case, `NO_SOLUTION`
  (`UNKNOWN`) — not exercised or specifically tested by the current fixtures at
  their present sizes, but a structural limitation worth flagging.
- **Solver determinism is not explicitly pinned.** No `random_seed` or
  `num_search_workers` parameter is set on the CP-SAT solver (Section 16); the
  determinism test passed 5/5 in this review, but the underlying non-determinism
  risk described in the prior-session lead is real and unaddressed in the code as
  of this review.
- **Rejection-reason text is a heuristic post-hoc reconstruction, not CP-SAT's
  actual internal reasoning.** CP-SAT does not natively expose a "why this specific
  block lost" trace; `solver.py`'s rejection-reason logic (Section 6) infers a
  plausible reason from the final variable assignment using a fixed priority order
  of checks (window fit → dependency → mutex → same-track competitor score → generic
  fallback). This is honestly a best-effort explanation, not a certified proof of
  causality, and the code itself frames it this way implicitly through its fallback
  case ("excluded by optimizer: capacity/priority trade-off").
- **A dead/unused parallel contract schema exists in the repo**
  (`contracts/block_candidate.py`, `common.py`, `optimization_request.py`,
  `optimization_result.py`, `disruption_event.py`) with overlapping class/enum
  names but incompatible field shapes and enum values versus the live
  `contracts/schemas.py`. This is a real maintainability hazard (Section 9.2) — not
  a functioning feature, but also not cleaned up.
- **`disruption_scenarios.json` documents disruption scenarios the backend does not
  support** (`ASSET_CONDITION_DETERIORATION`, `INFEASIBLE_SCENARIO`) — a fixture/
  design-doc that has outpaced the actually-implemented `DisruptionType` enum
  (Section 8).
- **CORS is fully open** (`allow_origins=["*"]` in `backend/app/api/main.py`) —
  reasonable for a local demo, not appropriate for a production deployment as-is.
- **No authentication/authorization anywhere in the API layer** — confirmed absent
  from all 3 routers and `main.py`.
- **No frontend automated test suite** (Section 14/16) — frontend correctness is
  currently only checked via TypeScript compilation (`next build`) and ESLint, not
  unit/integration/e2e tests.
- **The frontend's own `README.md` documents component names
  (`Timeline.tsx`, `KpiSummaryBar.tsx`, `ExplainabilityPanel.tsx`,
  `DisruptionControls.tsx`) that are deleted in the current uncommitted working
  tree** — that doc has not been updated to match the in-progress rewrite
  (Section 18). A team member reading only `frontend/README.md` would get a
  materially outdated picture of the current component structure.
- **All data is synthetic.** Explicitly stated by the project itself
  (README, `docs/demo-script.md`); asset positions, condition scores, defect
  severities, and failure histories are randomly sampled within plausible ranges
  by a seeded RNG, not sourced from real inspection records.
- **This branch is not `main` and is 5 commits ahead of `origin/main`, unpushed**
  (Section 18) — anyone checking out `main` directly will not see the `/recover`
  endpoint, the scoring/fixture alignment fix, the frontend disruption/recovery
  flow, or the Stitch UI redesign.

## 23. Team Handoff Guide

**Where to start reading (in this order):**
1. `README.md` — project framing and quick start.
2. `docs/architecture.md` and `docs/contracts.md` — system shape and the shared
   schema.
3. `contracts/schemas.py` — the actual, live data model everything else depends on.
4. `backend/app/optimizer/solver.py` — the core scheduling logic.
5. `backend/app/ml/scorer.py` + `backend/app/ml/features.py` — the scoring logic.
6. `backend/app/simulation/disruptions.py` + `simulator.py` — the recovery logic.
7. `backend/app/api/main.py` + `routers/` — how it's all wired to HTTP.
8. `frontend/src/lib/data.ts` + `frontend/src/components/DashboardClient.tsx` — how
   the frontend consumes it.

**Most important files (the ones almost everything else depends on):**
`contracts/schemas.py`, `backend/app/optimizer/solver.py`,
`backend/app/ml/scorer.py`, `backend/app/simulation/disruptions.py`,
`frontend/src/types/contracts.ts`.

**Data flow (one-line recap):** synthetic domain data → `ScoringFeatureAdapter` →
`score_block()` → scored `BlockCandidate`s in an `OptimizationRequest` →
`solve()` (CP-SAT) → `OptimizationResult` → HTTP → frontend `enrichData()` → UI.
Disruption: `OptimizationRequest` + `DisruptionEvent` → `apply_disruption()` →
mutated `OptimizationRequest` → `solve()` again → `OptimizationResult` → HTTP →
frontend `compareSchedules()` → UI.

**How to safely modify the solver:** `solve()` in
`backend/app/optimizer/solver.py` is the **single scheduling entry point** — per
`docs/integration.md`'s explicit rule, any new endpoint must call this function
rather than reimplementing scheduling logic. Before changing it, run
`python -m pytest backend/tests/test_solver.py backend/tests/test_optimizer_reoptimization.py -q`
(these two files encode every hard-constraint invariant the solver must preserve —
27 tests combined) and run the full suite (`python -m pytest -q`, 84 tests)
afterward. Do not add per-request objective-weight configuration without also
updating `contracts/schemas.py` (the live contract) — the unused Pydantic draft's
`ObjectiveWeights` model already sketches this idea but is not wired in.

**How to add/modify disruption behavior:** add a new handler function to
`backend/app/simulation/disruptions.py` following the existing 4-function pattern
(each takes `(request, event)`, returns an independent mutated copy via
`_copy_request()`, never mutates the input), add the new type to the
`DisruptionType` enum in `contracts/schemas.py` (and its TS mirror in
`frontend/src/types/contracts.ts`), wire it into `apply_disruption()`'s dispatch,
and add tests mirroring `test_simulation.py`'s existing per-type test pattern.
Remember `disruption_scenarios.json` already documents 2 unimplemented types
(`ASSET_CONDITION_DETERIORATION`, `INFEASIBLE_SCENARIO`) that could be a starting
point/spec if the team wants to close that gap.

**How the frontend connects to the backend:** `frontend/src/lib/data.ts` is the
single data-access layer — `fetchOptimizationData()` for `/optimize` (with fixture
fallback) and `triggerRecovery()` for `/recover` (no fallback, real errors
surfaced). `NEXT_PUBLIC_API_URL` controls the backend base URL.

**Files to treat carefully:**
- `contracts/schemas.py` — changing it is effectively an API version bump; every
  consumer (solver, simulation, API, frontend TS mirror, all fixtures) depends on
  its exact shape. `contracts/common.py`'s own docstring says as much for the draft
  files ("Treat changes to this package like an API version bump - sync with the
  team before editing") — the same caution applies even more to the live
  `schemas.py`.
- The 3 canonical fixtures (`corridor_a_blocks.json`, `corridor_b_dense.json`,
  `corridor_c_disrupted.json`) — if you regenerate them, you must keep
  `test_fixture_scores_match_canonical.py` passing (i.e. run the generator, don't
  hand-edit scores).
- Do not confuse `contracts/schemas.py` with the other 5 files in `contracts/` —
  they share class names but are incompatible drafts (Section 9.2).
- The uncommitted frontend working-tree state (Section 18) — anyone pulling this
  branch fresh via `git clone`/`git checkout` will **not** see `AppHeader.tsx`,
  `PlanView.tsx`, `DisruptRecoverView.tsx`, or the lib helpers unless these
  uncommitted changes are committed and pushed first; decide with the frontend
  owner (Archit) before committing/discarding them.

**How to run tests before changes:** `python -m pytest -q` (backend, ~2.3s, 84
tests) and `cd frontend && npm run lint && npm run build` (frontend, no unit tests
exist yet).

**Architectural assumptions not to casually break:**
- AI/ML scores are never a hard constraint — only an objective input
  (`docs/integration.md`'s explicit rule).
- `solve()` is the only scheduling entry point — no endpoint should reimplement
  CP-SAT logic inline.
- `contracts/` (specifically `schemas.py`) is the only schema surface for new
  endpoints — `docs/integration.md`: "never a new parallel schema that duplicates
  what a contract already says" (notably, this rule has already been violated once,
  historically, by the now-dead Pydantic draft files — don't repeat that pattern).
- Recovery/disruption never silently fakes success on the frontend — errors from
  `/recover` must be surfaced, not swallowed (this is deliberately different from
  `/optimize`'s fixture-fallback behavior, and that difference is intentional per
  `frontend/src/lib/data.ts`'s own comments).

## 25. Executive Summary

Pashupatastra is a working, end-to-end prototype for railway maintenance-block
scheduling built for SIH 2026 (Problem Statement SIH26027). What's actually built
and verified in this review: a FastAPI backend (`backend/app/api/main.py`) exposing
exactly three real HTTP routes — `GET /health`, `POST /optimize`, `POST /recover` —
backed by a genuine Google OR-Tools CP-SAT constraint solver
(`backend/app/optimizer/solver.py`) that enforces real hard constraints (track
no-overlap with configurable headway, possession-window containment, dependency
ordering, mutual-exclusion resource groups, and committed-block pinning across
re-optimization) and maximizes a combined priority+risk objective. Those
priority/risk scores come from a deterministic, fully explainable 7-feature
weighted-sum scoring function (`backend/app/ml/scorer.py::score_block`) — this is
correctly described as deterministic heuristic scoring, not a trained machine-
learning model (no training code, no model weights, no inference framework exist
anywhere in the repo). A disruption/recovery simulation layer
(`backend/app/simulation/`) supports 4 real disruption types (Asset Breakdown,
Track Unavailable, Emergency Work, Possession Curtailment), each of which mutates a
copy of the plan and re-solves it with the identical CP-SAT solver used for normal
planning — never a separate, weaker recovery algorithm. A Next.js/React frontend
consumes the live backend directly (with a fixture fallback only for the initial
PLAN view, never for recovery, which always surfaces real errors instead of faking
success), and provides a client-side before/after change classification
(PRESERVED/MOVED/NEWLY_SCHEDULED/DROPPED) for the disruption/recovery flow.

**What works today, verified by actually running it in this review:** 84/84 backend
tests pass (`python -m pytest -q`, 2.27s); the frontend builds cleanly
(`npm run build`) and lints with only 2 pre-existing cosmetic warnings
(`npm run lint`); the previously-flagged potentially-flaky determinism test passed
5/5 re-runs in isolation.

**Strongest technical achievements observed:** a genuinely constraint-correct CP-SAT
model (verified by dedicated invariant tests for every hard constraint, including a
test that the solver never mutates its own input); a real regression test
(`test_fixture_scores_match_canonical.py`) that keeps 3 checked-in demo fixtures
honest against the live scorer, specifically added after real drift was discovered
and fixed (commit `bdd05e0`); a recovery pipeline that reuses the exact same solver
rather than a special-cased shortcut, and a frontend that is explicit and honest
about live-vs-fixture data provenance rather than silently faking success.

**What remains limited:** the frontend has zero automated test coverage; a dead,
confusingly-named parallel Pydantic contract schema still sits unused in
`contracts/`; the current git working tree holds a substantial uncommitted
frontend rewrite (component deletions/additions) that is ahead of what
`frontend/README.md` documents; the system is single-corridor, synthetic-data-only,
has no real train-timetable/telemetry integration, and its solver has an
un-pinned random-seed determinism risk that has not (yet, in this review) actually
manifested as flakiness. The disruption-scenario fixture file documents 2 scenario
types the backend does not implement.

**What the team can confidently demo right now:** exactly the flow in
`docs/demo-script.md` — start both servers, show a live CP-SAT-optimized plan with
real per-block scoring explanations, trigger any of the 4 real disruption types,
show a live `/recover` call producing a genuinely re-solved plan with an honest
before/after comparison, and return to the original plan — all backed by real code
paths this review independently read and, where feasible, executed.
